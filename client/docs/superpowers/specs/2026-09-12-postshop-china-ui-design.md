# Postshop China — интерфейс раздела

Черновик проектного решения. 12 сентября 2026.

## Что делаем

Раздел «Postshop China» внутри существующей витрины: каталог товаров одного
внешнего поставщика (Taobao через посредника), которые продаются через нас, но
живут по своим правилам — своя корзина, свой заказ, свой срок доставки и лимит
веса на партию.

**Только интерфейс.** Бэкенда, таблиц и миграций в этой работе нет. API
поставщика ещё пишется, и он прямо предупредил, что поля будут меняться —
например, цена приедет разложенной на доставку и услугу. Раздел работает на
заготовленных данных: путь покупателя можно пройти целиком и показать, пока
API дописывают.

## Что решено и почему

| Развилка                 | Решение                                                | Довод                                                                                                                   |
| ------------------------ | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| Размещение               | отдельная группа маршрутов `/china/*` внутри витрины   | приём уже есть в проекте: `checkout/` и `profile/` лежат отдельными ветками вне `_base-layout`                          |
| Данные                   | статические фикстуры + слой-адаптер                    | слой обращения к API сгенерирован из схемы `postshop_mvp` и чужой формат обслужить не может — самописный слой неизбежен |
| Корзина                  | отдельное хранилище, свой ключ в браузере              | см. «Риски»: расширение существующей ломает перенос гостевой корзины                                                    |
| Варианты товара          | локальный компонент раздела, не платформенный механизм | вариантов нет ни в интерфейсе, ни в базе; обобщать не с чем, второго примера нет                                        |
| Модель оплаты и доставки | по свежему макету (12 сентября)                        | новее ТЗ; расхождение замкнуто в двух блоках оформления                                                                 |
| Мобильная вёрстка        | сразу, по приёмам витрины                              | макета для телефона нет, но витрина адаптивна — иначе раздел развалится                                                 |

Решения приняты после разбора тремя независимыми обзорами: долгосрочная
поддержка, риск для работающей витрины, скорость и объём переделок. Первые три
строки таблицы — единогласны.

### Расхождение, которое нужно закрыть

Свежий макет и присланное ранее ТЗ **противоречат друг другу**:

|                | ТЗ «PostShop China v4»                      | Макет от 12 сентября                                     |
| -------------- | ------------------------------------------- | -------------------------------------------------------- |
| Оплата         | только предоплата, наличных нет             | наличные, терминал, наличные + терминал                  |
| Доставка       | фрахт по весу, пошлина 4%, недельные партии | самолёт 20 TMT/кг за 10 дней, карго 10 TMT/кг за 25 дней |
| Порог согласия | есть, перед первым заказом                  | отсутствует                                              |

Верстаем по макету как по более свежему. Различие сосредоточено в двух блоках
экрана оформления — переделать потом дёшево. **Но модель должна быть
подтверждена** тем, кто писал ТЗ, до того как раздел покажут покупателям.

## Границы

**Делаем** семь экранов: главная раздела, категория с фильтрами, карточка
товара в трёх видах, оформление заказа, профиль с заказами. Плюс кнопка входа
в раздел на существующей главной витрины.

`Main (local stores)` из макета — это уже работающая главная витрины, а не
экран раздела; ей нужна только кнопка.

**Не делаем**, потому что нет в макете: поиск внутри раздела, избранное,
уведомления, возвраты и претензии, страницу условий доставки, вход и
регистрацию, экран выбора пункта выдачи, админскую модерацию товаров.
Ссылки на них в макете есть — ведут в никуда, это отмечено осознанно.

**Не делаем**, потому что рано: настоящий расчёт логистики (тарифы задаём
фикстурами), связь с общей корзиной витрины, постраничную загрузку каталога,
живые статусы заказа.

## Устройство

```
src/app/routes/china/
  route.tsx            раскладка раздела: своя шапка и своя корзина
  index.tsx            главная
  $categoryId.tsx      категория с фильтрами
  product.$productId.tsx
  checkout.tsx
  profile.tsx

src/pages/china-*/     содержимое экранов
src/widgets/China/     шапка раздела, боковая корзина, выбор варианта
src/shared/china/
  fixtures/            заготовленные товары и категории
  adapter.ts           формат поставщика → внутренний вид
  types.ts             внутренний вид
  cartStore.ts         корзина раздела
```

Общие шапка и подвал остаются от витрины — меняются логотип и кнопка возврата.

## Данные

Фикстуры собираются из настоящих примеров поставщика: `example-product.json`,
`example-catalog.json`, `example-categories.json`. Три случая из макета —
часы с размером и моделью, рубашка с размером, лампа только с цветом.

Между фикстурами и экранами стоит **адаптер**: принимает формат поставщика,
отдаёт внутренний вид. Компоненты знают только внутренний вид и никогда не
видят сырой формат.

Это единственная защита от обещанной смены полей: меняется один файл, экраны
не трогаем. Образец в проекте уже есть — `useCartData.ts` строит свою
вьюмодель поверх ответа бэкенда.

Внутренний вид товара, коротко:

```
id, name, description, images[]
price, oldPrice, discountPercent
weightG
optionGroups[]  — название группы и её значения
variants[]      — сочетание значений, своя цена, остаток, картинка
```

Поля поставщика, которые в него ложатся: `title`, `images`, `price.shelf`,
`weight_g`, `options`, `variants`, `stock`, `moq`, `compliance`.

## Корзина раздела

Отдельное хранилище со своим ключом. С корзиной витрины не пересекается
физически — как и требует ТЗ: «никогда не смешивается».

Хранит выбранный **вариант**, а не товар: у сочетаний разные цены и веса.
Считает общий вес и сравнивает с лимитом 10 кг, показывает полосу заполнения.

## Варианты товара

Компонент выбора с обычными пропсами, без китайских названий, живёт в папке
раздела. Два режима отображения: текстовые пилюли (размер, модель) и
картинки-образцы (цвет).

Недоступные сочетания приглушены и не нажимаются. При смене выбора меняются
цена, картинка и доступность.

Компонент написан так, чтобы переезд в общее место позже стоил недорого — но
**платформенный механизм вариантов здесь не проектируется**. Варианты для
своих товаров потребуют изменений в базе, корзине, позиции заказа и складском
учёте: это отдельная работа, и её объём от сегодняшнего решения не зависит.

## Общие места, которых касаемся

Только добавлением, без правки существующего поведения:

- кнопка входа в раздел в шапке витрины;
- новые ключи переводов (существующие не переименовываем);
- дерево маршрутов перегенерируется — проверить, что старые не переставились.

Китайские страницы **не импортируют** `setupApiClient`: у него перехватчики
авторизации и обновления токена, к заготовленным данным отношения не имеющие.

## Риски

**Общая корзина.** Если расширять существующую вместо отдельной, `syncToBackend`
при входе гостя отправляет каждую позицию на настоящий бэкенд. Незамеченный
китайский товар — запрос падает, и по текущей логике вся гостевая корзина не
переносится, включая настоящие товары. Ломается живой путь покупки. Отдельное
хранилище убирает риск полностью.

**Карточка товара** — узкое место работы. Механизма сочетаний в проекте нет
нигде, и именно его поставщик обещает переделать. Три дня из оценки приходятся
сюда, и здесь же оценка может уехать.

**Смена формата.** Обещана прямо. Закрывается адаптером.

## Порядок работ

|     | Этап                                      | Дней  |
| --- | ----------------------------------------- | ----- |
| 1   | фикстуры, адаптер, внутренние типы        | 1     |
| 2   | главная раздела                           | 1     |
| 3   | категория и боковая корзина               | 1.5   |
| 4   | карточка товара и механизм вариантов      | 3–3.5 |
| 5   | оформление: вес, доставка, разбивка суммы | 2     |
| 6   | профиль и детали заказа                   | 1     |
| 7   | адаптивность и шлифовка                   | 1.5   |

Итого 11–12 дней одним разработчиком.

## Открытые вопросы

1. Какая модель верна — предоплата с партиями или наличные с выбором
   самолёт/карго. Ответ нужен до показа покупателям.
2. Поставщик обещал слать цену разложенной. Свериться, чтобы наши поля
   совпали с его: `Jemi`, `Доставка`, `Скидка`, `Итого` из макета.
3. Вес приходит пустым; поставщик считает вес упаковки. Пока в фикстурах
   задаём вручную.
4. Файлы примеров пропали с диска — положить их в репозиторий рядом с
   адаптером, чтобы фикстуры делались с настоящих данных.
